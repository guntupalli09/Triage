# Step 4A.9.1 — Hybrid Discovery Architecture Proof of Concept: Final Report

Base commit (design + implementation + locked benchmark): `cd0825e`
Baseline (Step 4A.9 final) commit: `1c5d60e`

## A. Executive Summary

Built and tested a hybrid discovery architecture for indemnification
recognition: deterministic regex discovery (unchanged) + a bounded,
non-authoritative semantic-candidate-proposal layer + mandatory
deterministic verification, with a code-level authority boundary that
proved unbreakable under 13 targeted adversarial tests plus the full 200-
case benchmark and 80 hard negatives (0 authority-boundary violations,
0 new false positives, 0 regressions). Recall on genuinely fresh,
non-canonical positive phrasing improved measurably (false-absence rate
55.0% -> 25.0% on the locked benchmark's positives; 45.0% -> 75.0%
"discovered" rate) with zero cost to precision or determinism. The central
honest finding: **every single recall gain landed in REQUIRES_REVIEW, not
in a clean ACCEPT** — the deterministic verifier never let a semantically-
discovered ordinary-language span become an authoritative fact on its own,
which is the safest possible outcome but also means this POC has not yet
demonstrated the harder "broad discovery -> verified established fact"
half of the target architecture. A second honest finding governs the
verdict: because no real semantic/LLM provider is reachable from this
sandbox, the "semantic" layer is a hand-authored second vocabulary, and it
failed to recognize the benchmark's 30 deliberately novel-phrasing
positives (0/30) — exactly the case a real semantic provider exists to
solve. **Verdict: B — promising, more development hardening required.**
Step 4B does not begin.

## B. Environment Decision (Phase 0 addendum, see design doc Section 0)

genuine finding independent of that limitation.

## F. Phase 3 — Semantic Discovery Interface

`semantic_discovery.py`: `discover_candidate_spans(document_text, concept)
-> List[DiscoveryCandidate]`. `DiscoveryCandidate` is a frozen dataclass
with exactly 6 fields (`concept`, `evidence_span`, `start_offset`,
`end_offset`, `source`, `discovery_metadata`) — no party/side/cap/
multiplier/policy field exists on the type at all (not merely unused —
absent from the schema). `assert_authority_boundary_intact()` is a runtime
guard, also exercised as a test (`test_discovery_candidate_schema_is_
minimal`), that fails the build if that ever changes.

## G. Phase 4 — Evidence-Span Verification

`_verify_semantic_candidate` (indemnification_policy_engine.py) first
checks `text[start_offset:end_offset] == evidence_span` character-for-
character; any mismatch is `REJECTED` before any structuring regex ever
runs on it. Tested directly (`test_fabricated_quote_is_rejected`,
`test_bad_offsets_are_rejected`) and end-to-end via a monkeypatched
hallucinating discoverer (`test_end_to_end_hallucinated_candidate_never_
becomes_a_fact`).

Additive: regex discovery runs unchanged; `_run_semantic_discovery` always
also runs (Phase 8 requirement — not gated on regex failing first);

(VERIFIED/UNRESOLVED/REJECTED, Phase 10). `HYBRID_DISCOVERY_ENABLED` is a
single module-level flag so the regex-only arm above is exactly
reproducible, not approximated.

## Q. Phase 15 — Malicious/Hallucinated Discovery Attack Simulation

`semantic_discovery.py`'s `_fault_mode` parameter plus direct
`DiscoveryCandidate` construction in tests simulate: fabricated quote (not
in document) — REJECTED; bad offsets (out of document range) — REJECTED;
wrong concept label — REJECTED; malformed response (`None` instead of a
list) — treated as unavailable, `RECOGNITION_UNCERTAIN`, never
`CONFIRMED_ABSENT`; duplicated candidates (20x flood) — deduped to <=1
resulting obligation. All handled safely; none reached an authoritative
fact incorrectly.

## R. Phase 16 — Discovery Variability

10 full runs of the 200-case benchmark: byte-identical output every time
(1 unique hash across 10 runs). **Honest limitation**: because the
semantic layer in this POC is a deterministic regex-based simulation (see
Section B), this does NOT demonstrate that a real, genuinely probabilistic
provider's variability would be equally harmless — it demonstrates only
that the deterministic-verification layer itself introduces zero
variability of its own, which is necessary but not sufficient evidence for
a real-provider deployment.

## S. Phase 17 — Discovery Determinism vs. Authoritative Determinism

Discovery determinism: 100% in this POC (see Section R's caveat — an
artifact of simulation, not a property proven for a real provider).
Authoritative determinism: **100%, and by a stronger mechanism than "the
provider happened to be stable"** — verification only ever promotes a
candidate to VERIFIED via the same deterministic regex code the regex-only
path already uses, so even a genuinely non-deterministic real provider
could not make authoritative output non-deterministic on any candidate
that reaches VERIFIED; it could only change which spans get PROPOSED,
which changes recall run-to-run, not correctness of any accepted fact.
This is the key architectural property the whole POC exists to test, and
it held under every test performed.

## T. Phase 18 — Outage/Timeout/Malformed/Rate-Limited/Disabled Simulation

provider failure of any kind never silently becomes "provision absent";

## X. Phase 22 — Provenance Audit

Every `IndemnityObligation` now carries `discovery_source` (`REGEX` |
`SEMANTIC`), kept as a field ON the authoritative fact object (so it's
always visible in `category_treatments`/audit output) while remaining
structurally distinct from the `DiscoveryCandidate` that preceded it (a
`DiscoveryCandidate` is discarded once verification runs; only the
resulting `IndemnityObligation`, or nothing, survives) — satisfying the
"candidate discovery kept distinct from fact establishment" requirement.
The five provenance questions (what document, who discovered, who
verified, what evidence span, what code path) are all answerable from
`raw_excerpt` + `discovery_source` + the fact that verification is always
`_verify_semantic_candidate` (semantic path) or the direct structuring
loop (regex path) — no third path exists.

## Y. Phase 23 — Privacy/Data-Flow Audit

This POC's semantic layer runs in-process on text already fully available
to the deterministic engine; no network call, no third party, nothing
leaves the process — so there is no real privacy exposure to audit here,
and this report does not claim there would be none for a REAL provider
integration. A real integration would need: minimum-necessary text sent
(the local window, not the whole document), a contractual no-training-use
guarantee from the provider, and logging discipline that doesn't persist
full contract text longer than necessary. None of that is implemented or
provable here — flagged as unresolved for any future real-provider phase.

## Z. Phase 24 — Latency/Cost

Simulated component: sub-millisecond, in-process, effectively free — not
representative of a real provider (network round-trip + token cost per
call, likely tens to low-hundreds of ms and a small per-document token
cost for a focused single-concept scan). This POC does not produce a
usable cost estimate for a real integration; it only proves the
integration POINT (one call per document per concept) is architecturally
cheap to add.

## AA. Phase 25 — Cross-Adapter Applicability (not implemented)

The `DiscoveryCandidate`/verification pattern is concept-agnostic by
construction — `_verify_semantic_candidate`'s only indemnification-
specific parts are which structuring regexes it re-runs. The same
skeleton would apply to liability (basis/cap language), payment terms
(due-date/rate language), and, per Section U, likely also to the
chained-delegation and self-flagged-unresolved concepts that are currently
shared primitives in `policy_engine_core.py` — suggesting a shared,
core-level `verify_candidate_against(structuring_res, window)` helper
would avoid re-deriving this per adapter. Not implemented in this POC, per
the spec's explicit instruction.

## AD. Phase 28 — Three-Way Architecture Comparison

| Dimension | Current regex-centric | More regex hardening | Hybrid (this POC) |
|---|---|---|---|
| Generalization to unanticipated phrasing | Low (proven repeatedly, Step 4A.8/4A.9) | Low, improves only for phrasing the developer specifically adds | Low-to-medium *in this POC* (bounded by hand-authored vocab); architecturally capable of more with a real provider |
| Safety (false-clean-fact risk) | High confidence (deterministic) | High confidence | Equally high confidence — proven under adversarial testing, verification is the same deterministic code either way |
| False-absence rate | High on non-canonical phrasing (55% this benchmark) | Improves only for the specific phrases added | Meaningfully lower (25%) with zero new false positives |
| Precision (false positives) | Excellent | Excellent | Excellent — unchanged (0/80) |
| Automation rate (clean ACCEPT without review) | Unaffected | Improves slightly, phrase by phrase | Unaffected in this POC (0 semantic-sourced clean facts) |
| Determinism | 100% | 100% | 100% authoritative; discovery determinism untested for a real provider |
| Auditability | Good | Good | Good, plus explicit discovery-source provenance |
| Maintainability | Degrades over time (sunk-cost phrase-list growth, Step 4A.9's own finding) | Same failure mode, explicitly what Step 4A.9's verdict C rejected | Better in principle (one bounded interface vs. an ever-growing regex list) — not yet proven at scale |
| Cost/latency | Free | Free | Free in this simulation; unknown and nonzero for a real provider |
| Cross-adapter scalability | Requires re-deriving vocabulary per adapter (see Step 4A.9's parity matrix) | Same | Skeleton is concept-agnostic; not yet implemented across adapters |

Not favoring hybrid by default: on THIS benchmark, hybrid's measurable
advantage over "more regex hardening" is real but modest, and entirely
contained within REQUIRES_REVIEW routing (never a clean accept) — a
determined regex-hardening effort targeting the same `semantic_vocab`
phrase families would likely achieve a similar false-absence reduction
directly, at zero implementation complexity beyond what already exists,
though with the exact sunk-cost/enumeration-growth problem Step 4A.9's
verdict C was written to escape. Hybrid's genuine, structural advantage —
recognizing phrasing NO developer explicitly anticipated — is exactly what
this POC could not demonstrate, because it has no real semantic provider
to test with.

## AF. Phase 30 — Verdict

**B — promising, more development hardening required.** The authority-
boundary architecture is validated: it is safe to let a probabilistic
discovery layer propose candidates, bounded by mandatory deterministic
verification, with measurable recall benefit and zero measured cost to
precision, determinism, or auditability. It is not yet validated as
solving the generalization problem Step 4A.9 identified, because the only
"semantic" component available in this sandbox is a hand-authored
vocabulary that inherits the same fundamental limitation as regex: it only
recognizes phrasing someone thought to write down. Freezing for
independent validation (Step 4A.10) now would validate an architecture
whose central promise — recognizing genuinely novel phrasing — remains
empirically unproven.

## AG. Phase 31 — Next Steps (verdict B path)

What remains before a freeze decision is warranted:

   Step 4A.9-widened synonym patterns by concept — a real generalization

   verified via the semantic path) — a real provider might supply enough
   contextual signal that a widened (but still fully deterministic)
   verification pattern set could safely promote more semantic candidates
   to VERIFIED, not just to UNRESOLVED.
4. Only after (1)-(3): build a genuinely independent held-out validation
   corpus (Step 4A.10) and freeze.
