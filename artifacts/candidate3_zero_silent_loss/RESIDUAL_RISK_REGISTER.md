   - **An attempted fix was tried and reverted.** Broadening `_BREACH_ANCHOR_RE` for colloquial unauthorized-access phrasing, and `_BREACH_HOURS_RE`/`_BREACH_CALENDAR_DAYS_RE` for a "let X know" colloquial notify-verb, was implemented and then found NOT to actually close the gap once tested end-to-end: `_classify_breach_notification`'s anchor check receives a `window` that starts AT the `_ANCHOR_RE` match position, so a colloquial anchor phrase requiring backward context ("someone got into" preceding "personal data") falls entirely outside the window the function actually sees. This is the same "window direction masking" defect class a prior mission fixed for the negation check specifically (by passing a separate, backward-widened `negation_scan_text`), but the ANCHOR check itself was never given the same treatment.
   - **Why not fixed properly in this mission**: correctly fixing this requires either (a) widening the anchor-check window backward similarly to how negation scanning already does, and re-verifying this doesn't cause the anchor to fire on unrelated nearby text in longer real documents, or (b) redesigning `_any_established`'s scope to check specifically whether the admitted candidate's OWN concept was structured, not any unrelated dimension (the deeper, more general fix — see below). Neither was safe to attempt and verify within this mission's remaining time in an adapter (`data_security`) untouched by every other change this mission made, given the demonstrated risk of shipping an unverified change (found by directly testing the first attempt and confirming it didn't work).
   - **Recommended follow-up**: a properly scoped mission to (1) generalize the negation-checker's backward-scan-window pattern to the anchor check itself across all adapters that have this same "check requires backward context relative to the ANCHOR_RE match position" shape, and (2) redesign each adapter's `_any_established`-style absence-state check to be scoped to the SPECIFIC admitted candidate's own concept rather than "any dimension in this adapter," which is the deeper, more general fix underlying both `ip_ownership-080`'s original mechanism and this new `data_security-139` finding.
