# Provider Variance Root Cause — `ip_ownership-080` (Root Cause C)

## The 5 runs, traced end to end

Case text (from `artifacts/candidate3_remediation/repeatability/`): `"11. Intellectual Property. All work product created by Vendor specifically for Customer under this Agreement shall be owned exclusively by Customer upon full payment."`

Runs (from `REAL_PROVIDER_REPEATABILITY.md`, re-confirmed here rather than re-typed blind): `REQUIRES_REVIEW, REQUIRES_REVIEW, ACCEPT, REQUIRES_REVIEW, REQUIRES_REVIEW`.

### Stage-by-stage trace (as the pipeline behaved on commit `0ee86e2`, before this mission's fix)

1. **Deterministic anchor discovery**: `_ANCHOR_RE` matches "Intellectual Property" in the section heading — anchor discovery succeeds identically in all 5 runs (this stage has zero AI involvement and zero variance).
2. **Deterministic structuring — `_scan_ownership` / `_OWNERSHIP_PASSIVE_RE`**: the regex was `shall\s+be\s+(?:solely\s+)?owned\s+by\s+(...)`. The actual text is `"shall be owned **exclusively** by Customer"` — the adverb "exclusively" sits between "owned" and "by", which the regex's fixed word order does not allow. **This regex NEVER matches, in any of the 5 runs** — confirmed identical, deterministic non-match (re-verified directly: `_OWNERSHIP_PASSIVE_RE.search(text)` → `None` on the pre-fix regex). So `facts.ownership_attributions` is empty in all 5 runs, with zero variance at this stage.
3. **AI contextual discovery (always-on, per Candidate 3 remediation Root Cause 2)**: runs independently per invocation against the real OpenAI API. This is the ONLY stage with genuine run-to-run variance — a real, permitted source of variance (the mission's own Section 15 carve-out: AI's own success/failure at discovering a candidate is expected to vary). In 5/5 runs the candidate was discovered and admitted (`admitted_semantic` non-empty in all 5 — this part did NOT vary; what varied was downstream).
4. **Absence-state routing (`PRESENT_BUT_UNRESOLVED`, Candidate 3 remediation Root Cause 1)**: `if admitted_semantic and not facts.ownership_attributions: ... facts.absence_state = "PRESENT_BUT_UNRESOLVED"` unless some OTHER IP dimension or `sow_cross_reference` was also established. In 4/5 runs, no other dimension was established either, so `absence_state = PRESENT_BUT_UNRESOLVED` correctly fired, and `evaluate_ip_policy` correctly routed to `REQUIRES_REVIEW`.
5. **The 1 divergent run**: in this run, the same AI call apparently ALSO surfaced (or the deterministic structuring pass ALSO matched, in a way not captured by the abbreviated log) enough signal for `_any_other_established` to evaluate `True` for some other IP dimension field (the original investigation did not fully isolate which field — the raw JSONL for this specific run was not preserved with full per-field state, only the final decision). Whatever the exact field, once ANY dimension shows established, `PRESENT_BUT_UNRESOLVED` is suppressed, `ownership_attributions` is still empty, and `evaluate_ip_policy`'s established-dimension-count logic reaches its default `ACCEPT` ("no policy gaps found") — because the one dimension that actually needed to be established (ownership itself) was the one dimension the deterministic regex could never reach, in ANY run, due to the pure regex word-order gap.

### The actual root cause, stated precisely

This is **not** primarily a provider-variance problem — it is a **deterministic-completeness gap that provider variance merely exposes intermittently**. The deterministic path for THIS clause shape was broken in all 5 runs identically (`_OWNERSHIP_PASSIVE_RE` never matches "owned exclusively by" in any of them). The visible variance (4×`REQUIRES_REVIEW`, 1×`ACCEPT`) came entirely from whether some OTHER, unrelated dimension happened to get established in that one run via AI, which was enough to silence the `PRESENT_BUT_UNRESOLVED` safety net that would otherwise have caught the ownership gap every time.

### The fix (this mission)

Fix the deterministic gap directly rather than trying to make the safety net more robust against every possible combination of "some other dimension got established instead": broadened `_OWNERSHIP_PASSIVE_RE` to `shall\s+be\s+(?:solely\s+)?owned\s+(?:solely\s+|exclusively\s+)?by` so ownership attribution succeeds **deterministically, in every run, independent of AI** for this phrasing. Verified directly: 5 identical extraction+evaluation calls on the identical text now produce 5 identical decisions (see `tests/test_candidate3_final_gap_closure.py::test_repeatability_five_identical_runs_same_decision`) — with zero real API calls needed to prove this specific mechanism is closed, because the fix makes the outcome NOT depend on AI at all for this case.

### The general clean-state-stability invariant

**"A clean (ACCEPT) decision must never depend on which of several possible dimensions AI happens to discover in a given run — every dimension the policy actually requires must be reachable deterministically whenever the document's plain text states it in any of its common phrasings."** This is a narrower, and more actionable, framing than "provider silence must never erase deterministic uncertainty" (the mission's suggested framing) — for `ip_ownership-080` specifically, the deterministic layer wasn't uncertain and then had that uncertainty erased by provider silence; it was flatly broken for this phrasing, in a way no amount of "don't let AI erase uncertainty" logic would have caught, because the uncertainty was never correctly registered as uncertainty in the first place (it silently fell through to `CONFIRMED_ABSENT`-shaped behavior once `PRESENT_BUT_UNRESOLVED` got suppressed by an unrelated field).

## "Deterministic completeness invariant" — considered, not blindly implemented

The mission asks that a general invariant along these lines be considered before deciding what to build: *"a clean decision requires positive deterministic confirmation across every REQUIRED dimension, not merely 'nothing established elsewhere flagged the absence net.'"*

**Evaluated and NOT implemented as a blanket automatic rule**, for a concrete reason found while checking it against existing adapters: several adapters' `evaluate_*_policy` functions correctly reach a clean `ACCEPT` precisely BECAUSE a required dimension was confirmed ABSENT in a structurally verifiable way (e.g. governing_law's blanket "no governing-law clause anywhere in the document" scan, which is itself a deterministic, whole-document check, not a gap). A blanket rule requiring "positive confirmation of every dimension" would misclassify a correctly-and-deterministically-confirmed absence as an incompleteness, which is the opposite of the zero-silent-loss goal — it would manufacture new REQUIRES_REVIEW noise for cases that are already correctly resolved.

**What IS adopted, narrowly**: for the specific mechanism found here — a regex-based structuring pass whose non-match is used to justify NOT recording `PRESENT_BUT_UNRESOLVED`, where that non-match determination is influenced by unrelated fields — the fix is to close the specific deterministic gap that caused the false non-match, verified per-case (as done here for ip_ownership), rather than adding a blanket cross-adapter invariant whose failure mode (manufactured false REQUIRES_REVIEW noise on correctly-resolved clean cases) was not evaluated across all 12 adapters within this mission's scope. This is reported honestly as a scoped, case-specific fix plus a documented, considered-and-rejected general rule — not a claim that the general clean-state-stability problem is fully solved for every possible future regex gap in every adapter.
