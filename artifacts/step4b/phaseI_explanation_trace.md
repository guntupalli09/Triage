# Step 4B Phase I — Explanation Fidelity: Read-Only Trace

## Explanation paths identified

| Path | Component classification |
|---|---|
| `rules_engine.analyze()` finding rationale (`finding.rationale`) | **DERIVED-DETERMINISTIC** — templated text keyed to which rule fired, no LLM involvement. |
| `policy_enforcement._finding_from_decision`'s `explanation`/`required_action` | **DERIVED-DETERMINISTIC** — generated by the adapter itself from the matched category/treatment, never LLM. |
| `interaction_enforcement._finding_from_interaction_decision`'s `explanation` | **DERIVED-DETERMINISTIC** — generated by the firing interaction rule's own predicate. |
| `evaluator.LLMEvaluator.evaluate()` (`summary_bullets`, `top_issues[].why_it_matters`, `possible_missing_sections`) | **NON-AUTHORITATIVE LLM NARRATION** — explicitly documented as such in the module's own comments ("LLM must never detect risks, only explain pre-identified findings"). |
| `evaluator.create_fallback_response` | **DERIVED-DETERMINISTIC** — builds the same shape as the LLM path but pulls every field straight from the deterministic finding, used whenever the LLM is unavailable or produces zero findings. |
| `main.build_enhanced_issues` (merges the above for `results.html`/`review.html`/`shared_report.html`) | **Boundary function** — decides which fields are authoritative (severity, title — after this phase's fix) vs. narration passthrough (`why_it_matters`). |
| `review_queue.build_review_queue` | **AUTHORITATIVE** — reads `policy_state`/`clause_type`/`interaction_id` directly from the raw persisted findings, never touches `build_enhanced_issues`'s output or any LLM content at all (confirmed already in Phase 0/F). |
| PDF report (`main._build_pdf_bytes`) | Consumes `all_issues` (the output of `build_enhanced_issues`) — inherits whatever protection that function provides. |
| Shared report (`shared_report.html`) | Same `build_enhanced_issues` output, same inherited protection. |
| Dashboard/history/listing summaries | Read `Contract.overall_risk` and (after the Step 4B dashboard integration) `document_aggregation`'s output directly — never touch LLM content at all. |

## Defects found and fixed

### 1. Fabricated top_issues were never actually filtered

`evaluator.LLMEvaluator._verify_output_maps_to_findings` — despite its own
docstring describing it as "VERIFICATION 5," it only logged a
`logger.warning` for a non-mapping LLM `top_issue` and then
**unconditionally `return True`** regardless of what it found. Its caller
(`evaluate()`) discarded that return value entirely. Net effect: a
hallucinated finding with no basis in any real deterministic rule would be
displayed to the user exactly as if it were a real, explained finding.
Reproduced directly before fixing.

**Fix**: the function now mutates `llm_output["top_issues"]` in place,
dropping any issue that does not map to a real finding, and returns
whether anything was dropped — enforced in the one place that already has
both the LLM output and the canonical mapping, so it holds regardless of
whether a caller checks the return value.

### 2. Empty `rule_name`/title silently matched everything

While building the benchmark for defect #1, a second, more fundamental
bug surfaced: `_normalize_title("")` returns `""`, and Python's `"" in x`
is always `True`. Any finding lacking a `rule_name` (or with an empty
title) contributed an empty string into the matching sets, which then
caused **every** LLM issue title to trivially "match" via the
substring-containment check — silently defeating the entire verification
for any finding shaped that way, independent of defect #1.

**Fix**: empty normalized values are now explicitly excluded from the
`normalized_rule_names`/`normalized_titles`/`normalized_aliases` sets
before matching.

### 3. Displayed finding title could be entirely LLM-authored

`main.build_enhanced_issues`: when an LLM explanation matched a
deterministic finding (via fuzzy substring matching, not exact equality),
`enhanced = llm_issue.copy()` made the **LLM's own title text** — not the
deterministic finding's title — the value rendered as the finding's
headline (`results.html`'s `<h3>{{ issue.title }}</h3>`). Since the
match check only requires the two titles to loosely overlap, an LLM
title reframing the conclusion (e.g., turning "Uncapped Liability Clause"
into "...is fully mitigated and safe") could still pass the match check
while displaying a contradicted headline.

**Fix**: `enhanced["title"]` is now always forced to
`finding.get("title", "")` — the deterministic value — exactly like
`severity` already was. The LLM's own free-text narrative
(`why_it_matters`) is left untouched; only the declarative conclusion
statement is protected.

## Confirmed already correct (no fix needed)

- `overall_risk`: `evaluate()` already unconditionally forces
  `result["overall_risk"] = overall_risk` (the deterministic value)
  regardless of what the model returned.
- `disclaimer`: `_validate_result` already unconditionally forces it to
  the fixed safe string.
- Evidence/citation fields (`exact_snippet`, `matched_excerpt`,
  `evidence`, `party_direction`, `clause_number`) are never sourced from
  `llm_issue` at all — the merge code only ever reads them from `finding`.
- `policy_state`/`clause_type`/`interaction_id` are never part of
  `build_enhanced_issues`'s output contract at all (confirmed:
  `results.html` never references them) — the review queue
  (`review_queue.build_review_queue`) is the authoritative path for those
  fields, reading them directly from raw persisted `findings_json`,
  completely independent of any LLM content.
- Malformed/missing-key model output already raises inside
  `_validate_result` and is caught by `evaluate()`'s own `except Exception`,
  falling back to `None` (main.py then calls `create_fallback_response`).
