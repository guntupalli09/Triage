# Provider-Variance Design (Candidate 3 remediation)

## Chosen mechanism: (A) deterministic canonicalization of the ADMITTED outcome + (F) deterministic absence rule — NOT multi-sampling

Per Section 8's instruction to evaluate designs and "choose the smallest architecture that proves the invariant," and its explicit caution against "automatically mak[ing] multiple API calls for every production review unless necessary": **this remediation does NOT add a second/third real-provider call per review.** A single document review continues to make exactly the same number of real-provider calls as before this remediation (Root Cause 2's fix widens WHEN discovery is attempted per adapter per review, from "only if zero anchors" to "always," but that is a per-review-count change already required independently, not an anti-variance mechanism).

The anti-variance mechanism is purely **downstream and deterministic**:

1. **(A) Deterministic canonicalization of the ADMITTED outcome.** Once `fact_admission.evaluate_admission()` has ruled a candidate `ADMITTED` (ESTABLISHED + grounded + no unresolved dependency/conflict + all qualifiers grounded — an already fully deterministic gate, unaffected by this remediation), that candidate's downstream treatment must be a **pure function of its own admitted content**, never of "did today's process also independently rediscover the same thing via regex." Concretely: `PRESENT_BUT_UNRESOLVED` (see `CANONICAL_PRIMARY_FACT_SCHEMA.md`) is assigned whenever an admitted candidate exists and the narrow value regex does not match — deterministically, every time, given the same admitted candidate content, regardless of which run produced it.

2. **(F) Deterministic absence rule: AI silence never independently establishes `CONFIRMED_ABSENT`.** This rule is **already correctly implemented** in all 11 shared-framework adapters today (confirmed in `PRE_IMPLEMENTATION_MAP.md`): `CONFIRMED_ABSENT` requires BOTH the deterministic anchor regex AND semantic discovery to find nothing (`if not admitted_semantic and not unresolved_dependency_note: return None` only after semantic discovery genuinely ran and returned empty — a provider error instead routes to `RECOGNITION_UNCERTAIN`). This remediation does not weaken it, and re-verifies it stays true once Root Cause 2's "always attempt discovery" change is applied (a case with deterministic anchors present no longer skips semantic discovery, so it is now ALSO possible for semantic discovery to add material to an already-anchored case — handled via the reconciliation rules in Section 6 of the mission, implemented as: admitted AI candidates and deterministic anchors are merged into one candidate list and deduplicated by overlapping span, never by one channel silently overriding the other).

## Why NOT (B), (C), (D), or (E)

- **(B) deterministic completeness requirements for clean decisions** — already effectively true (an adapter only reaches ACCEPT when its own required fields are populated); no additional mechanism needed once (A) is in place.
- **(C) corroboration requirements for high-stakes facts** — would require a second real-provider call specifically for "high-stakes" facts, which the mission asks to avoid unless necessary; (A)+(F) prove the invariant without it.
- **(D) targeted second-pass AI verification only when discovery channels disagree** — "disagreement" in Section 15's sense is ACROSS independent runs of the SAME review, which a single production review never observes (it only ever makes the discovery/verification calls once per adapter per review). There is no within-review signal to trigger a second pass from. This mechanism would only be meaningful if production reviews already made multiple calls, which they don't and this remediation doesn't add.
- **(E) explicit `DISCOVERY_UNCERTAIN` state when provider-dependent candidate presence affects the policy result** — this is subsumed by `PRESENT_BUT_UNRESOLVED`, which is the concrete, adapter-consumable form this idea takes once Root Cause 1's mechanism is understood precisely (see `CANONICAL_PRIMARY_FACT_SCHEMA.md`). A separate `DISCOVERY_UNCERTAIN` state was considered and rejected as redundant with `PRESENT_BUT_UNRESOLVED` + `RECOGNITION_UNCERTAIN` (which already exists for the "provider errored" case) — adding a third, overlapping state would fragment `evaluate_*_policy()`'s branching without adding safety.

## What residual variance remains, and why it is acceptable per the mission's own terms

Given (A)+(F), the ONLY remaining cross-run variance for the identical input is: **whether a given real-provider call, this particular time, successfully discovers and admits a genuinely-present-but-unusually-phrased clause at all.** When it does: `PRESENT_BUT_UNRESOLVED` → `REQUIRES_REVIEW`, consistently. When it doesn't (the model's sampling simply misses it that run, or returns a non-ESTABLISHED verification): the existing, unchanged `CONFIRMED_ABSENT` path applies, consistently for THAT information state. The cross-run outcome pair is therefore always drawn from `{REQUIRES_REVIEW, NOT_APPLICABLE}` (or `{REQUIRES_REVIEW, CONFIRMED_ABSENT}` pre-adapter-decision) — **never** `{ACCEPT, NOT_APPLICABLE}`, `{ACCEPT, NEGOTIATE}`, or any pair including a CLEAN state, which is the specific, exhaustively-enumerated hard-fail condition in Section 7. This is exactly the outcome Section 15 explicitly excuses: "If provider variance exposes unresolved material uncertainty and all such runs safely route to review, that is acceptable" — reframed here as "safely route to review OR safely remain absent," since a genuine recall miss on an unusually-phrased, AI-only-discoverable clause is a recall limitation to be improved over time (wider corpora, better prompts, a stronger model), not a safety violation to be architecturally eliminated by adding cost/latency to every production review.
